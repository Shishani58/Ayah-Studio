# FULL20×3: другие чтецы и причина ошибок

## Цель

Проверить, переносится ли включённый FULL QPC20с×3 соШатри на других чтецов;
отделить влияние workers от изменения длины/границ акустических участков.
Только read-only эксперименты: production, настройки, канонический текст и
пользовательские БД не менять. Вывод ограничить проверенными записями.

## Прочитано

- `AGENTS.md`, `RTK.md`, `docs/project.md`, full-performance и задачи предыдущих
  измерений/включения: новаяstrong-политика, batch1/global norm, реальныеflags.
- `tools/bench_full_windows.py`, `references.py`: benchmark пока жёстко
  использовал эталонШатри, нужен явный reference и production guards.
- Каталог `/Users/ayub/Developer/quran_flutter/assets/data/reciters/reciters-base.json`:
  соответствующие друг другу audio_url и timecodes_url для каждой записи.
- Только114 файловШатри доступны локально. Данные для других записей будут
  кешированы отдельно; urllib TLS не прошёл, curl с обычной проверкойTLS работает.

## Решения и план

- Четыре новых записи: Саадаль-Гамиди, Мухаммадаль-Миншауи murattal,
  Махмудаль-Хусари, Абдуль-Басит mujawwad. Суры80/98/112: средняя с короткими
  аятами, длинные аяты, короткая запись.54 аята на запись,216 уникальных границ.
- Использовать audio/timecodes именно из одной записи по каталогуQuranAcademy.
  Сравнить скачанный reference с packaged DB поSHA/строкам; не подменять запись
  только по совпадению имени чтеца. Все эталоны загружаются после model inference.
- Минимальная факторная матрица: strong10/20/30×1/×3 плюс прежний fixed30×1.
  Один процесс наcase с тремя сурами, pinned QPC INT8, context2,batch1,
  штатныйintra-op pool. При20с одни и те же окна в×1/×3; это чистая проверка
  параллельности. Длины10/20/30 при одинаковых workers изолируют длину/границы.
- Дляstrong включить production guard60с и те же FULL review checks;
  raw/final warnings сохранять отдельно. Обычный benchmark безфлага не менять.
- Ошибки к независимому эталону, число/порядок аятов, точное совпадение
  emissions/timings/confidence/flags/окон при×1/×3, новые>500мс, unflagged,
  фактические окна/паузы и источники/хэши. Не выбиратьчтецов только по успеху.
- При ошибке сохранитьfailure ипричину; отсутствие пауз/защитный отказ>60с
  не объявлять численной ошибкой из-запараллельности.

## Результат

Подробности —[report.md](report.md). Завершены28 процессов/84 выравнивания
сур/1512 оценённых предсказаний для216 уникальных начал (4 записи×54).
Новых исключений/нарушений числа/порядка аятов нет. Все эталоны структурно
валидны, строки совпали с packaged DB, URL/хэши сохранены. Аудио/runtime
кешированы вне Git. Замороженная копия runtime/данных после тестов неизменна;
первому запуску не хватало pyproject-маркера checkout, исправлено до предсказаний.

36 точных сравнений×1/×3 (31 многоконное,27 с>=3 окнами): одинаковые emissions,
rows/confidence, raw/final flags, checks и физические окна. Ошибки не вызваны
параллельностью на проверенном CPU/QPC.20×3 быстрее20×1 на31.06–34.73%
в этих одиночных процессах. Точный timing gain без повторов не обобщается.

Для20×3: Гамиди median/max68.5/240мс,0/54 ошибок>500мс; Миншауи108.5/343мс,
0/54; Хусари235/1483мс,12/54; mujawwad1484.5/4331мс,52/54. Старый fixed30
имел1/0/12/51 крупную ошибку соответственно. Все64 текущих крупных расхождения
с ревью (старый оставлял12 без флага). У mujawwad80:41 новая threshold-regression
+461→+581мс, flagged; у Гамиди устранена прежняя80:42+1900мс.

Длина/места участков иногда меняют результат независимо от workers:
Гамиди80:31−67→−647мс при10с и80:27−125→−825мс при30с; обе ошибки flagged
и одинаковы в×1/×3. Это не простое обрезание слова устыка: GT в3.4/10.9с
от ближайшего разреза. Конкретный внутренний вклад контекста/INT8 этим
опытом не разделялся. У Хусари/mujawwad большинство расхождений существовало
до изменения окон:63 из64 крупных GT внутри принятых пауз,58 CTC-маркеров
внутри той же паузы. Положение начала в длинной тишине —важная часть причины,
но это DSP-анализ, не ручная проверка всех слов/границ.

Реальный process_surah(full) на98 каждого чтеца точно совпал с20×3 benchmark.
Рекомендация —оставить20×3; точность для любых114 сур/других записей не обещать.
Следующая задача качества —границы внутри длинных пауз/неоднозначная привязка,
не возврат к последовательным вызовам. Production здесь не менялся.

Проверка:45 целевых тестов,Ruff,source/data/model/audio/reference hashes,
36 parity pairs,4 actual pipeline checks,diff-check. Блокеров нет.
