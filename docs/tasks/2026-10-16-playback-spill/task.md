# Начало следующего аята в конце воспроизведения

## Цель
Воспроизвести жалобу на нескольких переходах Фатихи Шатри после FULL v9.
Проверить обе части: фактические cuts и точность остановки плеера.
Исправить подтверждённую причину без записи пользовательской БД/ручных меток,
смены модели и новых зависимостей. Не трогать параллельные изменения.

## Evidence и прочитанные материалы
AGENTS/CLAUDE, RTK; docs/project.md (контракт общих границ и FULL), предыдущие
waveform-boundaries результаты. Активный API53140: Шатри/full/QPC; сохранённая
Фатиха действительно v9:120,6483,11460,15937,21577,27740,33395мс.
app.js scheduleAyahStop/finishAyahPlayback: HTMLMediaElement + setTimeout,
повторный timeupdate; точность остановки пока не измерена.

## План
- [x] Сохранены read-only baseline/trace, волны всех6 переходов и SHA.
- [x] WebKit воспроизвёл позднюю остановку; Chromium этого масштаба не показал.
- [x] Конечный WAV вместо остановки целого MP3 по JS-часам; absolute/pending seek
  сохраняет координаты волны, выбора, скорости и ручных правок.
- [x] 7 реальных PCM ranges,12 коротких WebKit previews с busy UI,6 полных
  переходов штатными функциями;58 целевых и948 общих pytest/10 skipped.

## Решения
Gain automation по HTML currentTime исследована и отклонена: WebKit clocks
могут расходиться с фактическим звуком. Сохранён только диагностический
gain-prototype.js; production его не импортирует. Конечный WAV не содержит
отсчётов за правой границей. Непрерывное чтение использует исходный файл.
Проверять огибающую недостаточно для доказательства правильности всех cuts;
новая правка устраняет выход плеера за метку, не объявляет весь FULL точным.

## Сохранность
Аудио SHA прежний. БД во время работы изменилась извне: те же7 времён Фатихи
получили updated_at22:17:44Z вместо22:09:11Z. Все наши пробы read-only;
обратной записи/восстановления пользовательской БД не было.
