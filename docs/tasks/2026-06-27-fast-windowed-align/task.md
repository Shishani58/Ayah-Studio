# Быстрый режим: адаптивное оконное выравнивание

## Цель
«Быстрый» режим генерации: нейросеть гоняется не по всему аудио, а по узким окнам
вокруг предсказанных границ аятов; экономия процессорного времени при приемлемой
точности. По выбору пользователя (валидированный фаза-4 трек).

## Актуальный статус
Новая версия прототипа (паузы → онсет волны + растущее окно от 1 с) реализована
в `surah_cutter/core/align_fast.py` и подключена как `mode='fast'` в pipeline и
web-GUI. Режим доступен рядом с `full` как экспериментальный быстрый вариант.

Ограничение остаётся: распевные суры (например 80/87) могут давать off-by-one
серии при высокой conf, поэтому `full` остаётся точным режимом по умолчанию.

## Замеры (де-риск, до реализации)
- Размещение границы по паузе напрямую (слепо): медиана **3–6 с** — негодно.
- Точность онсета паузы при ИДЕАЛЬНОМ сопоставлении (потолок): медиана **217 мс**,
  p90 324, max ~3900 (wasl — границы без паузы).
- Предсказание по ГЛОБАЛЬНОМУ среднему темпу (доля символов × длительность):
  медиана **3389 мс** — не работает (темп неравномерный, распев).
- Предсказание по АДАПТИВНОМУ темпу (от предыдущей подтверждённой границы):
  медиана **468 мс**, p90 1838, max 4876. → окно ±2с ловит ~90% границ.

Вывод: жизнеспособен только адаптивный оконный вариант — точку ставит нейросеть
(точность ~57мс сохраняется), скорость ~1.5–2× (окна < полного аудио). Wasl и
промахи окна → расширение/полное выравнивание.

## Алгоритм (core/align_fast.py)
1. Якорь: выровнять первые K аятов от 0 (с префиксом-басмалой) → онсеты + старт темпа.
2. Идём по аятам: предсказать онсет = пред.граница + символы(пред.аят) × темп.
3. Срез аудио = окно вокруг предсказания (ширина ≥ локального текста + margin).
4. Нейровыравнивание локальных слов (хвост пред.аята + голова текущего) на срезе →
   онсет текущего аята (старт его первого слова) + уверенность.
5. Граница у края среза / низкая уверенность → расширить окно и повторить; крайний
   фоллбэк — полное выравнивание остатка.
6. Переякориться: пересчитать темп по подтверждённой границе. Монотонность.

## Контракт
`align_surah_fast(pcm, sr, words, *, surah, ...) -> [(ayah, start_ms, conf)]`
— та же сигнатура/выход, что `align.align_surah`. Подключается в pipeline как
`mode='fast'`; в UI показан ручной выбор `точно/быстро`.

## Критерий приёмки (на эталоне Шатри, джуз Амма)
Включаем «быстрый» режим, только если: медиана ≤ ~150 мс, p95 ≤ ~500 мс (цель
проекта) И ускорение ≥ 1.5× против full. Иначе — не включаем, остаёмся на «только
точно». Корректность Корана — приоритет: при сомнении не ускоряем.

## Старый прототип: отклонён

Прототип `core/align_fast.py` прогнан на сурах 78/90/93/100 vs эталон:
- точность: медиана **десятки секунд** (окна промахиваются, прогноз уезжает,
  фоллбэк со смещением) — катастрофа;
- скорость: **0.38–0.57× (медленнее в ~2.5×)**.

Корень — фундаментальный, не баг:
1. Накладные расходы запуска ONNX на КАЖДОЕ окно (~1с×N границ) > один полный проход.
2. Чтобы амортизировать — нужен батч всех окон, но адаптивный прогноз (нужен для
   точности) вычисляет окна последовательно → батчить нельзя. Без адаптивности
   прогноз уезжает на 3.4с → окна мимо.

Решение на тот момент: НЕ включаем. Остаёмся на «только точно». UI-тоггл убран.
Старый вариант `align_fast.py` был оставлен как артефакт на случай смены модели —
реальное ускорение ожидалось только от более быстрой акустической модели.
