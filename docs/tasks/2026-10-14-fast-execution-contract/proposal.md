# Единый исполнитель FAST и найденные проблемы

Дата: 14 октября 2026 года. Версия 2 после ревью по текущей рабочей копии.
Статус: уточнённый план; общий исполнитель ещё не реализован.

Выбрано направление: один исполнитель управляет алгоритмом FAST для всех
моделей, а явные состояния ограничивают порядок его действий. Адаптеры дают
акустические доказательства и не управляют обработкой суры. Это закрепляет
порядок работы при добавлении моделей. Критерии подтверждения входят в общий
контракт; калибровка качества конкретной модели проверяется отдельно.

Документ объединяет выбранное направление и проблемы, найденные в текущей
рабочей копии. Интерфейсы и переходы общего исполнителя ещё не реализованы;
выполнен только описанный ниже этап M1a существующего guard.
Первый приоритет — исполнимые правила доказательств, бюджета и завершения,
затем один исполнитель. Исправления, необходимые для выполнения этих правил,
входят в перенос; остальные улучшения качества проходят отдельно.
Документ не разрешает переписывать весь FAST одним изменением.

## Вывод ревью и изменения версии 2

Направление верное: общий исполнитель устраняет различие бизнес-алгоритмов
при смене модели. Хорошо сохранены локальность FAST, независимое акустическое
наблюдение, защита ручных меток и различие между фактом и confidence.
Главный недостаток первой версии — подробная схема состояний без полностью
определённых условий принятия, завершения, сохранения и включения нового пути.

| ID | Проблема первой версии и доказательство | Изменение плана |
|---|---|---|
| R01 | Миграция требует минимальной различающей фразы и отказа от глобального каркаса, но P04–P14 отложены до её завершения | Необходимые для инвариантов правила реализуются вместе с циклом; это изменение поведения, не механический перенос |
| R02 | До M1a `LocalAcousticReads.read` / `LocalWhisperReads.read` списывали бюджет после успешного ответа; ошибка и отмена после inference теряли реальное чтение | Исправлено в M1a: начатый вызов расходует бюджет независимо от результата |
| R03 | `write_alignment_result` сначала делает commit SQLite, потом `os.replace` JSON/log; `FAILED` не гарантирует отсутствие сохранённых данных | Разделить расчёт и сохранение, определить точку commit и отдельный исход ошибки диагностики |
| R04 | `process_surah` накладывает frozen-метки после расчёта; writer повторно читает защиту под транзакцией | Валидировать отдельно модельный результат и окончательный merge; ручная метка не обязана быть центром модельной паузы |
| R05 | `server._generation_modes` учитывает `requested_mode`, но не версию FAST, модель или настройки | Версия должна участвовать в ключе возобновления; иначе новый исполнитель может вообще не запуститься |
| R06 | `EXPAND_LOCAL` / `RESOLVE_BLOCK` могут вернуться к тем же данным; cache hits не расходуют бюджет | Конечный набор кандидатов/расширений и запрет повторного решения без новых данных |
| R07 | Confidence и capability-флаг не задают проверяемое доказательство; у Whisper нет эквивалентной CTC временной привязки | Общая структура доказательства и требования для pause / wasl / first_onset; unsupported — ревью |
| R08 | 65% покрытия не гарантирует ни малый cache, ни локальный смысл чтений; CTC cache хранит все emissions | Отдельно учитывать причину чтения, память cache и всю историю бюджета; удаление cache не возвращает бюджет |
| R09 | Прежний корпус — один чтец, в основном 78–114; точность будущего цикла неизвестна | Парное сравнение ошибок и покрытия, новые edge cases, явные ворота включения, без обещания улучшения по старым цифрам |

R01, R06–R09 — пробелы спецификации, а не уже воспроизведённые ошибки нового
кода. R02–R05 подтверждены указанными функциями при ревью, R02 затем исправлен.
Старые замеры ниже сохранены как исторические данные и повторно этим ревью
не измерялись.

Рабочие решения для первой реализации: строгая остановка после неразрешённого
блока; длинная пауза не даёт исключения из 6 секунд; fingerprint не сдвигает
pause-метку в новом пути; ручные данные защищены. Это консервативные решения
этого плана, а не приписанное пользователю согласие со всеми положениями
предыдущего документа. Изменение существующих явных режимов в первый этап
не входит. [Исполнение и проверки](../2026-10-14-fast-contract-review/task.md).

Строки относятся к рабочей копии при подготовке документа. Символы позволяют
найти соответствующий код после последующих изменений.

CTC выполняет поиск пауз, локальный anchor первого аята, чтение всех активных
trusted-пауз, построение опор и последовательный matcher. Затем он подключает
слабые/micro-паузы, оценивает темп, повторяет matcher, выполняет wasl/refine и
многочисленные repairs. В конце возвращает pause-метки к центрам, формирует
ревью и результат.

Tarteel читает все принятые паузы, расширяет некоторые локальные чтения,
выбирает монотонную цепочку опор и интерполирует остальные метки. У него нет
полноценного общего с CTC последовательного recovery и wasl-выравнивания.
Изменение модели поэтому меняет и порядок исполнения FAST.

## Выбранная архитектура

Единственная точка входа FAST вызывает один исполнитель. GUI, CLI, старый Qt
и benchmark используют её. Выбор модели меняет только подключённый адаптер.
FULL, tiled, reference и пословный режим остаются отдельными явно выбранными
режимами; адаптер FAST не может автоматически переключить на них запуск.

| Участник | Ответственность |
|---|---|
| Исполнитель FAST | Текущий аят, план фразы, выбор пауз, расширение, recovery, решение, метки и переходы; возвращает результат без сохранения |
| Общие операции с текстом | Канонические слова, сравнение начал и повторов, необходимое различие |
| Общий DSP/VAD | Кандидаты пауз и их интервалы; тишина сама не доказывает номер аята |
| Общий шлюз локальных чтений | Отрезок PCM, guard, cache, учёт реальных вызовов, отмена и диагностика |
| Адаптер модели | Представление текста для модели, локальный decode и доступные локальные акустические операции |
| Общая проверка результата | Полнота, порядок, интервалы, вид доказательства и признаки ревью |
| Orchestration запуска и существующий writer | Отмена, валидация merge, транзакционное сохранение и защита edited/verified; публикация диагностики после commit |

Исполнитель не должен снова вырасти в функцию с независимыми циклами
«CTC FAST» и «Whisper FAST». Различия модели выражаются данными и акустическими
возможностями. Порядок шагов, определение подтверждённой границы и правила
продвижения принадлежат исполнителю.

Для этого достаточно stdlib, небольших типов данных и явных переходов.
Отдельный фреймворк состояний, универсальная система плагинов и новые
зависимости не требуются. Названия новых модулей выбираются при реализации;
они не являются частью поведенческого контракта.

### Плюсы и ограничения

Одна правка порядка исполнения действует для всех адаптеров. По переходам
видно, почему аят подтверждён или остановлен. Новый адаптер проходит тот же
набор сценариев и не может незаметно принести собственный алгоритм.

Ошибка общего исполнителя затронет все модели. Перенос требует отделить
акустические операции от решений в двух существующих реализациях. Общий
формат результатов должен учитывать, что не всякая модель надёжно даёт
временные позиции или одинаковые оценки качества. Жёсткие переходы требуют
заранее описанного recovery, иначе они могут блокировать законные случаи.

## Алгоритм из 12 шагов

Это целевой порядок, зафиксированный в исходном предложении. Текущий запрос
пользователя разрешает его ревью и улучшение, а не подтверждает автоматически
каждую формулировку. Изменение порядка явно отражается в версии контракта.

1. **Подготовить данные.** Декодировать аудио в 16 кГц mono. Получить слова,
   порядок и число аятов из базы Корана.
2. **Найти паузы.** Определить начало и конец кандидатов по громкости и DSP/VAD,
   разделить на надёжные и слабые. Речевая модель пока не вызывается.
3. **Найти первый аят.** Отделить вступление и басмалу, если она не является
   аятом. Подтвердить начало первого аята коротким локальным чтением.
4. **Взять следующий аят.** Обрабатывать строго по порядку. Не перескакивать
   через неподтверждённый аят.
5. **Определить, что услышать.** Выбрать минимальную фразу до различающего
   слова с учётом похожих начал и повторов внутри аята.
6. **Выбрать паузу.** Искать после предыдущей подтверждённой границы.
   Использовать темп для прогноза области поиска, но не для доказательства.
7. **Прочитать короткий фрагмент.** Начать с начала выбранной паузы,
   захватить достаточно речи после её конца и сопоставить с нужной фразой.
8. **Принять решение.** Подтверждён текущий аят — назначить паузу;
   продолжение предыдущего — проверить другую; неоднозначность — расширить;
   будущий аят — разобраться с пропущенным участком.
9. **Разрешить сложный участок.** Совместно сопоставить соседние аяты и
   паузы; для соединённых аятов выровнять короткий wasl-блок. Недостаток
   доказательств или превышение бюджета означает ревью.
10. **Поставить метку.** Подтверждённая пауза — её центр; подтверждённый
    wasl — начало первого слова; предварительная оценка — confidence=0 и ревью.
11. **Перейти дальше.** Использовать надёжные границы как опоры, обновить темп
    и повторять шаги 4–10.
12. **Проверить и сохранить.** Проверить число аятов, порядок и привязку к
    паузам; сохранить причины сомнений; не перезаписывать ручные метки.

Для версии 2 после исчерпания recovery подтверждение хвоста останавливается.
Продолжение через независимо доказанную правую границу остаётся отдельным
будущим изменением политики, проверяемым на корпусе.

## Явные состояния и переходы

Состояние — что исполнитель делает сейчас. Результат аята — какой факт
установлен. Эти понятия разделяются: состояние чтения само не означает,
что аят найден.

| Состояние | Действие | Допустимый выход |
|---|---|---|
| `PREPARE` | PCM, канонический текст, снимок настроек | `DETECT_PAUSES` |
| `DETECT_PAUSES` | Только DSP/VAD | `LOCATE_FIRST` |
| `LOCATE_FIRST` | Выбрать гипотезы первого начала | `PLAN_PHRASE` с фазой первого аята |
| `PLAN_PHRASE` | Определить необходимое текстовое различие | `SELECT_CANDIDATE` |
| `SELECT_CANDIDATE` | Выбрать следующую паузу либо гипотезу начала | `READ_LOCAL`, `RESOLVE_BLOCK` или `REVIEW_REQUIRED` |
| `READ_LOCAL` | Получить локальное доказательство через guard | `EVALUATE` или `REVIEW_REQUIRED` при отказе без доступного recovery |
| `EVALUATE` | Проверить фразу, альтернативы и временную привязку | `CONFIRMED`, `SELECT_CANDIDATE`, `EXPAND_LOCAL`, `RESOLVE_BLOCK` или `REVIEW_REQUIRED` |
| `EXPAND_LOCAL` | Запланировать обоснованное расширение | `READ_LOCAL` либо `REVIEW_REQUIRED` |
| `RESOLVE_BLOCK` | Разрешить текущий короткий блок без пропуска | `READ_LOCAL`, `CONFIRMED` или `REVIEW_REQUIRED` |
| `CONFIRMED` | Сформировать метку из доказательства | `ADVANCE` |
| `ADVANCE` | Обновить опоры/темп, увеличить текущий номер | `PLAN_PHRASE` либо `VALIDATE` |
| `REVIEW_REQUIRED` | Зафиксировать недостаточность и confidence=0 | По явно выбранной политике нерешённого участка |
| `VALIDATE` | Проверить модельный результат | `RESULT_READY` либо `FAILED` |
| `RESULT_READY` | Вернуть результат вызывающему коду | Конец работы исполнителя; это ещё не сохранение |
| `FAILED`, `CANCELLED` | Ошибка либо отмена расчёта | Новых чтений и передачи результата writer нет |

Состояния `SAVE` и `DONE` принадлежат orchestration запуска. Его контракт
commit описан ниже; executor не получает БД и не вызывает writer.

Первый аят проходит те же чтения и оценку, но с контекстом вступления.
Если он начинается без паузы, его доказанное первое слово имеет отдельный
вид `first_onset`; оно не объявляется wasl с несуществующим предыдущим аятом.

`RESOLVE_BLOCK` может получить речь будущего аята как правую гипотезу.
Пока текущий аят не разрешён, будущая граница не публикуется как опора для
дальнейшего продвижения. Подтверждённый короткий блок применяется целиком,
с проверкой всех его границ и публикацией аятов в каноническом порядке.

### Политика нерешённого участка

Рабочая политика версии 2 для соблюдения шага 4: после исчерпания
локального recovery текущий аят получает ревью; дальнейшие акустические
подтверждения этого запуска останавливаются. Для оставшегося хвоста можно
сохранить предварительные оценки с confidence=0 и причиной
`blocked_by_unresolved_ayah`. Они не становятся опорами. Ранее подтверждённые
метки сохраняют свой статус доказательства.

Альтернатива для обсуждения: разрешить продолжение после явно закрытого
ревью-блока, используя независимо доказанную правую границу. Это ослабление
буквального шага 4 и отдельная политика контракта. Его нельзя включить
внутри нового адаптера. Этот переход не входит в первую реализацию.

Остановка подтверждения хвоста может резко увеличить ревью длинной суры.
Это известная цена строгой политики; её надо измерить отдельно от точности.
Нельзя называть перенос успешным только потому, что он перестал подтверждать
почти всё. Для предварительного хвоста используется детерминированный prior
в свободном интервале, с сохранением подтверждённых меток. Если в интервале
нет достаточного числа различных целых миллисекунд, результат не сохраняется:
`unrepresentable_timeline`, без сдвига подтверждённых границ.

### Конечность исполнения

Каждый аят/блок имеет конечный список кандидатов и ступеней расширения,
зафиксированный в конфигурации. Повтор того же `(аят/блок, кандидат, окно,
фраза, операция)` без новых данных запрещён. Cache hit сам по себе не является
новым доказательством. Ветка либо использует ещё не проверенный кандидат,
расширяет различающий контекст в пределах лимита, подтверждает блок, либо
завершается ревью. Блок ограничен и числом аятов, и разрешённым аудиоокном;
границы атомарно публикуются только после валидации всех его участников.
Конкретные конечные лимиты фиксируются на этапе M0, до реализации цикла.
Тест с постоянно неоднозначным fake-адаптером обязан завершаться даже при
доступном cache. Ошибка модели не превращается в бесконечный retry.

## Контракт адаптера

Интерфейс ограничивает полномочия, а не только приводит аргументы к одному
формату. Конкретные Python-типы определяются при реализации; минимально
достаточны следующие операции и результаты.

| Операция | Вход | Выход и ограничение |
|---|---|---|
| Представить известную фразу | Канонические слова выбранного контекста | Единицы модели и карта единица → исходное слово; канонический текст не изменяется |
| Прочитать локальное аудио | Только разрешённый PCM-фрагмент, фиксированные параметры декодирования | Независимо услышанные единицы, доступные позиции и показатели качества |
| Сопоставить локальные доказательства с известным текстом | Уже полученные локальные данные и выбранная фраза/короткий блок | Акустические соответствия, полнота пути и доступные позиции либо явное отсутствие возможности |

Сопоставление на кешированных emissions не является новым inference.
Если операция требует ещё одного вызова модели, он также проходит общий
шлюз и учёт бюджета. Внутренние вычисления декодера допустимы, скрытые новые
аудиоокна — нет. Подсказанное известным текстом распознавание не считается
независимым подтверждением того же текста.

Адаптер не получает весь PCM суры, writer, список всех пауз или право
двигать текущий аят. Он не решает, расширять ли окно, принять ли границу,
какую паузу взять, куда поставить метку и нужно ли включить FULL.

CTC и Whisper могут иметь разные акустические возможности. Адаптер явно
сообщает, доступны ли временные позиции и локальное выравнивание, насколько
полон вывод и как трактуется его собственная оценка качества. Отсутствие
операции означает недостаточность доказательств для соответствующей ветки,
а не другой алгоритм. Глобальная цепочка опор, интерполяция и критерии
приёма вроде текущего `_rank()['confirmed']` должны выйти из адаптеров.

Нормализация для сравнения допустима только на копии текста. Полученное
распознавание никогда не заменяет текст Корана. Оценки разных моделей
нельзя автоматически считать одной калиброванной вероятностью.

### Минимальное доказательство границы

Общий результат аята содержит `ayah`, `start_ms`, `evidence_kind`, `review_reason`,
ссылки на реально выполненные чтения и модельные показатели качества с их
происхождением. Подтверждение — отдельное решение исполнителя, не `conf > 0`.
Акустически подтверждённое не становится пользовательским `status=verified`:
writer продолжает записывать автоматические метки со статусом `auto`.

| Вид | Что обязательно проверить |
|---|---|
| `pause` | ID и окончательный DSP-интервал паузы, её владелец, полная различающая фраза после паузы, проверенные конкуренты; время строго в округлённом центре |
| `wasl` | Доказательство идентичности соседнего текста и локальная временная привязка первого слова текущего аята; наличие forced-path само по себе недостаточно |
| `first_onset` | Отличие от интро/басмалы, первое слово и его локальная позиция; если адаптер не даёт позицию, одно узнавание текста не подтверждает время |
| `estimate` | Только целая допустимая оценка, confidence=0 и конкретная причина; не используется для темпа или будущих акустических опор |

Нормализованная единица хранит соответствие каноническому слову. Пропуск
различающей единицы не компенсируется высокой средней similarity. Конкуренты
включают начала соседних аятов и внутренние повторы релевантного контекста;
схлопывание разных слов нормализацией само является неоднозначностью.
«Независимый» означает decode без подсказки нужной фразы, а не статистическую
независимость от forced alignment на тех же emissions.

CTC и ASR могут использовать разные измерители и фиксированные пороги качества,
но общие требования полноты, различимости и временного доказательства.
Пороги задаются версией политики исполнителя для вида измерителя, не скрытым
`confirmed` внутри адаптера. Пока они не проверены на baseline, новый путь
экспериментальный. Отсутствие timing-capability не имитируется нулевым временем.

### Бюджет, cache и координаты

Шлюз принадлежит одному запуску с неизменяемыми PCM, моделью и параметрами.
Внутри суры не создаётся новый шлюз для сброса лимитов. Все операции адаптера,
включая дополнительные локальные decode/align, проходят тот же учёт.

- Интервал в целых samples — `[s0, s1)`. Проверяются конечность, направление,
  допустимость после ограничения границами PCM и фактическая длина перед
  каждым dispatch. В trace раздельны запрошенный и реально переданный интервалы.
- До dispatch проверяется отмена. Начатая попытка резервирует sum и union;
  при ошибке/отмене резерв не возвращается, потому что модель могла уже прочитать
  вход. Записывается исход `completed`, `failed` или `cancelled`; отказ guard
  не считается вызовом. Если backend нельзя измерить изнутри, это консервативный
  учёт отправленного входа, а не заявление об успешном inference.
- После возврата проверяется отмена до cache/публикации доказательства. Отмена
  проверяется и перед cache hit. Реальные повторные вызовы расходуют sum;
  успешный cache hit — нет. Первый исполнитель последовательный; при добавлении
  параллельности проверка и резервирование должны стать атомарными.
- Cache привязан к модели/revision, PCM, параметрам и операции. CTC-срез
  содержит ссылку на исходное чтение, абсолютную сетку frames и применённый lag.
  Срез контекстных emissions не объявляется эквивалентом нового inference
  узкого окна. ASR-текст большого окна нельзя обрезать как emissions без
  временной привязки; совпавших координат недостаточно для другой операции.
- Cache ограничивается памятью; удаление старых emissions не удаляет ledger
  чтений и не возвращает бюджет. Число cache hits/отказов и peak cache bytes
  диагностируются. Размер лимита фиксируется в M0, а не выбирается по записи.

6 секунд включают паузу, pre-roll и речь. В первой версии нового пути длинная
пауза, из-за которой фраза не помещается, даёт `insufficient_local_context`;
сама по себе она не разрешает обрезать различающее слово или увеличить лимит.
Чтение только конца паузы может быть отдельной последующей политикой. На очень
короткой суре 65% может не хватить даже на минимальную фразу: честное ревью,
без исключения для коротких файлов. Для wasl без паузы нужен конкретный
локальный прогноз от подтверждённой опоры; регулярное сканирование всей речи
окнами не допускается, даже если каждый запрос короче 6 секунд.

## Обязательные инварианты

1. Канонический текст, порядок и число аятов принадлежат базе Корана.
   Рабочий результат на суру содержит её точный набор; полный строгий экспорт
   содержит 114 сур и 6236 аятов.
2. DSP/VAD выполняется до первого речевого чтения. Модель читает только
   выбранный локальный участок для текущего решения или его recovery.
3. Нет предварительного речевого чтения всех пауз, полного emissions-pass,
   последовательного покрытия всей записи или скрытого FULL/tiled fallback.
4. Guard сохраняет текущие жёсткие ограничения: отдельное чтение до 6 секунд,
   объединённое покрытие до 65%, суммарный вход с повторениями до 200%
   длительности. Целая запись не разрешается даже при длине меньше 6 секунд.
   Эти пределы не означают целевую долю чтения: читать нужно минимально.
5. Расширение имеет конкретную причину. Похожий текст сам по себе не
   разрешает читать больше на каждой посторонней паузе.
6. Подтверждение требует достаточной различающей фразы и отсутствия сильного
   противоречия. Темп, тишина, similarity и полный forced-path по отдельности
   не доказывают владельца границы.
7. Пауза и её владелец — один факт. Метка равна округлённому центру конечного
   интервала. Wasl требует доказанного начала первого слова.
8. Предварительные оценки имеют confidence=0, причину ревью и не становятся
   акустическими опорами. Номер аята меняет только исполнитель.
9. Проверяются `0 <= start_ms < duration_ms`, строгий порядок и доступность
   целочисленных меток для всех аятов. Невозможность представить полный набор
   внутри записи означает ошибку валидации, а не метки после конца файла.
10. Edited/verified защищены существующей транзакцией. До commit ошибка,
    отмена или конфликт не публикуют частично изменённые тайминги текущей суры.
    Ошибка sidecar после commit не означает откат SQLite.

Бюджет, отмена и инварианты проверяются при выполнении. Тесты дополнительно
выявляют изменения маршрутизации и обходы интерфейса. Сам по себе `Protocol`
не делает вызовы обходного кода технически невозможными.

## Валидация, сохранение и отмена

Валидация модельного результата выполняется до наложения ручных данных:
точный канонический набор, целые времена, порядок, диапазон по длительности
декодированного PCM и доказательства каждого подтверждения. NaN/inf,
неполный набор, несовпадение trace и итоговых rows — ошибка, не тихий repair.
Метка после квантования остаётся внутри записи; две подтверждённые метки,
попавшие в одну миллисекунду, требуют пересмотра доказательства/ревью, а не +1 мс.

В транзакции writer повторно читает актуальные edited/verified и проверяет
эффективный merge, включая временной диапазон. Ручная метка сохраняет своё
происхождение и не проходит проверку «центр модельной паузы». Конфликт с ней
не разрешается её сдвигом. Исходный модельный результат и фактически сохранённые
метки различаются в диагностике; GUI не получает модельную confidence для
ручного времени. В первой реализации защищённые метки не используются как
акустические опоры: привязка пользовательской разметки к исходному аудио
не доказана одним статусом `verified`.

Единица транзакции — сура, не весь пакет. Суры, успешно сохранённые ранее
в пакете, остаются после отмены следующей. Точка принятия сохранения — commit
SQLite. Проверка отмены нужна перед началом записи и непосредственно перед
commit; запрос, пришедший после последней проверки, может проиграть commit.
В таком случае исход честно сообщает, что сура сохранена; он не обещает откат.

JSON/log не находятся в одной транзакции с SQLite. Если их публикация после
commit не удалась, orchestration возвращает `saved_with_diagnostics_error`
с путями и ошибкой, не общий «не сохранено», и не перезапускает модель автоматически.
Это отдельная доработка этапа M4; нынешний writer так пока не сообщает.
Отменённые/ошибочные чтения сохраняются в диагностике запуска по возможности,
но не публикуются как успешный alignment-run. Ошибка самой диагностики
не должна скрывать первоначальную ошибку модели.

## Диагностика и версия алгоритма

У результата должны быть отдельные версии алгоритма FAST, адаптера и модели.
Изменение порядка шагов, допустимых переходов, правил подтверждения либо
размещения метки требует изменения версии алгоритма. Замена весов модели
сама по себе не означает изменение алгоритма; она фиксируется в provenance.

Снимок запуска сохраняет эффективные параметры, включая значения из env,
бюджет, нормализацию, lag, модель/revision и подпись исходного аудио.
Конфигурация не меняется в середине суры. Подпись size/mtime идентифицирует
файл слабее криптографического хэша; для воспроизводимого benchmark сохраняют
хэш, как в существующих корпусных отчётах. Снимок включает также хэш
канонического текста/транслитерации, версию DSP/VAD и конфигурацию декодирования.
Модельный bundle привязывается в начале запуска: последующее изменение
`ACTIVE_ID` не меняет вычисление или source уже запущенной суры.

Для каждого решения записываются текущий аят, состояние и причина перехода,
проверенные кандидаты, необходимая фраза/слово, реальные интервалы чтения,
cache hits, отказы guard, альтернативы и итоговое доказательство. Переход
`REVIEW_REQUIRED` содержит конкретную причину, а не только низкую confidence.
Результат для GUI, trace и writer собирается из одного итогового объекта.

Версия помогает воспроизвести изменение, но сама не предотвращает его.
Защиту дают единый исполнитель, ограничения зависимостей, сценарные тесты
и явная проверка изменений контракта при ревью.

Ключ возобновления включает алгоритм/адаптер/модель, эффективные настройки,
идентичность аудио и канонических данных. Совпадения `requested_mode=fast`
недостаточно. Legacy или несовпадающий ключ пересчитывает только auto-метки;
полностью защищённая сура сохраняется без перезаписи. Это проверяется для
Web/CLI/Qt до включения нового пути, а не только записывается в JSON.
Старые JSON-прогоны остаются читаемыми; отсутствующие поля обозначаются как
неизвестные. Версия JSON-доказательств отдельна от SQLite `db_version`.

## Каталог найденных проблем

Обозначения: **дефект** — воспроизведённое поведение либо прямое расхождение
с указанным правилом; **риск** — механизм в коде без доказанной частоты ошибок;
**ограничение** — отсутствующая возможность; **развилка** — противоречие
между текущим поведением и требуемым контрактом.

### P01 Раздвоение исполнения

**Дефект архитектуры.** `align_surah_fast` выбирает отдельный Tarteel-путь,
который владеет собственными циклами, matcher, цепочкой опор и интерполяцией.
Источник: `align_fast.py:5525` и `align_fast_whisper.py:92`.
Исправление: единый исполнитель; адаптеры оставляют только акустические
операции. Необходимые для инвариантов дефекты устраняются вместе с новым
циклом; обёртка над двумя прежними циклами не решает P01.

### P02 Продвижение через неподтверждённый аят

**Дефект относительно шага 4.** `_sequential_pause_match` может увеличить
текущий номер после неудачного восстановления и сохранить будущую опору.
Источник: `align_fast.py:5268,5430,5466`.
В синтетическом воспроизведении helper вернул `[None, 2000]`: первая граница
не подтверждена, вторая имеет действие `deferred_future_anchor`.
Это доказательство поведения matcher, а не утверждение об итоговой ошибке
полного пайплайна на конкретной записи.
Исправление: переходы и явная политика нерешённого блока; будущая гипотеза
не даёт права скрыто пропустить текущий аят.

### P03 Предварительное чтение всех пауз

**Расхождение со шагами 4–7 и риск расхода бюджета.**
`build_anchor_skeleton` декодирует все активные паузы; Tarteel читает все
принятые кандидаты до последовательного решения.
Источник: `align_fast.py:6236`, `align_fast_whisper.py:129`.
Guard предотвращает полное покрытие записи, поэтому это не обнаруженный
полный emissions-pass. Но ненужные внутренние остановки конкурируют за
бюджет с recovery; влияние на конкретную ошибку требует отдельного trace.
Исправление: чтения по запросу текущего решения, обновление темпа по мере
подтверждения и повторное использование только разрешённых локальных данных.

### P04 Высокая similarity без различающего слова

**Риск ложного подтверждения.** `_sim_ij` прекращает расширение при высоком
сходстве, не имея обязательного общего признака «различающее слово услышано».
Источник: `align_fast.py:6095` и `core/phonetics.py:onset_similarity`.
Синтетический общий префикс без различающего окончания получил similarity
около 0,909 при обычном пороге подтверждения 0,50. Это демонстрация слабости
критерия; последующие проверки иногда могут отклонить такое совпадение.
Исправление: обязательная полнота необходимой фразы, качество различающего
слова, независимое наблюдение и проверка конкурирующих продолжений.

### P05 Несогласованные размеры локального окна

**Дефект.** `_build_pause_read_plan` ограничивает речь, затем прибавляет паузу;
`LocalAcousticReads` ограничивает весь запрос. Пауза 2 с плюс речь 4,5 с
дала окно 6,5 с при `maximum_window_ms=6000`; guard отказал
с `nonlocal_window`.
Источник: `align_fast.py:584`, `fast_reads.py:61`.
Исправление: планировать полную длительность. Если необходимая фраза не
помещается, выбирать допустимый recovery либо ревью с конкретной причиной.
Не обрезать различающее слово и не повышать confidence за неполное чтение.

### P06 Предположения о вступлении и первый аят

**Дефект правила размещения и риск неверной опоры.** При отсутствии intro-owner
CTC использует предположение о 6,5 с вступления. `_first_ayah_content_start`
переносит начало до 6 с на 6000 мс независимо от переданной confidence.
В helper-воспроизведении 2800 мс с confidence=0,99 стало 6000 мс.
Первый энерго-кандидат также специально рассматривается как intro-пауза;
это не текстовое доказательство басмалы.
Источник: `align_fast.py:5677,2034`, `candidates.py:294`;
Tarteel выбирает похожую исходную гипотезу в `align_fast_whisper.py:150`.
Исправление: локально подтвердить первое начало, проверить варианты без
вступительной басмалы; длительность вступления оставить прогнозом. Для сур
1 и 9 сохранить канонические правила. Искусственный сдвиг не остаётся
подтверждённой границей.

### P07 Запрет расширения короткого полного слова Tarteel

**Дефект.** `إِنَّ` нормализуется в `ان`: целое слово распознано,
`complete_words=1`, но два символа не проходят обязательное `prefix_chars>=3`.
Аят 2:6 поэтому не получает расширение даже при высокой token confidence.
Источник: `align_fast_whisper.py:133`, сохранённая диагностика Tiny.
Исправление: достаточность короткого слова определять по токенам/акустике;
наличие целого слова может разрешить чтение различающего продолжения,
но само не подтверждает границу.

### P08 Отклонение точной фразы по символьному margin

**Дефект критерия Tarteel.** Точные начала 2:11 и 2:13 имеют similarity=1,
но margin около 0,043 ниже порога 0,12. Конкуренты могут не содержать полного
нужного префикса, однако символьное сходство мешает принять правильный.
Источник: `align_fast_whisper.py:58`; случаи повторены на текущем `_rank`.
Исправление: сравнивать реальную полноту и различающие слова релевантных
альтернатив. Margin оставить дополнительным сигналом, а не единственным
вето для доказанной различающей фразы.

### P09 Статическая неоднозначность до шести слов

**Ограничение.** `_phrases` фиксирует максимум шесть слов и флаг `ambiguous`.
Для начал 2:68–70 этого недостаточно; дополнительный услышанный текст не
расширяет саму целевую фразу и не снимает флаг.
Источник: `align_fast_whisper.py:38`.
Исправление: общий план фразы до реального различия, текущая последовательность
и проверка внутренних повторов. Если отличие не помещается в разрешённое
аудио, короткий совместный блок либо явное ревью.

### P10 Ошибки ASR и точное совпадение слов

**Ограничение модели и matcher.** Tiny искажает либо сливает слова.
Сохранённые примеры: аят 2:197 — «الْحَيُّ» вместо целевого «الحج»;
2:249 — слияние слов. Строгий `complete_words` не подтверждает границы.
Источник: `align_fast_whisper.py:58` и диагностика Tiny.
Исправление: сравнение нормализованных токенов/единиц, проверка различия,
обоснованное расширение и локальное выравнивание при наличии возможности.
Нечёткое сходство не разрешает игнорировать существенное различающее слово;
неустранимая ошибка модели остаётся для ревью.

### P11 Wasl CTC запрашивает слишком широкий промежуток

**Ограничение текущей реализации.** `fill_wasl_run` берёт контекст от левой
опоры до правой с текстом предыдущего аята. Даже одна недостающая граница
может дать запрос шире 6 с и отказ guard. Далее остаётся prior с confidence=0.
Источник: `align_fast.py:9171`.
Исправление: короткий достаточный хвост предыдущего аята и начало текущего;
при повторяющемся хвосте не сужать контекст без доказательств. Слишком широкий
или неразрешимый блок остаётся для ревью, без скрытого полного выравнивания.

### P12 У Tarteel отсутствуют общие recovery wasl и темп

**Ограничение и расхождение со шагами 6,9,11.** После цепочки опор Tarteel
интерполирует недоказанное через `expected_boundary_fractions` и `np.interp`.
Нет общего последовательного recovery, измеряемого по мере исполнения темпа
и совместного wasl-выравнивания; trace показывает `n_wasl=0`.
Источник: `align_fast_whisper.py:150–201`.
Исправление: эти решения принадлежат исполнителю. Модель с неподходящей
временной привязкой честно возвращает недостаточность для wasl.
Интерполяция допустима только как явно обозначенный предварительный результат.

### P13 Поздняя повторная фраза может стать опорой

**Риск и наблюдаемое расхождение с эталоном.** Монотонная цепочка максимального
суммарного сходства не доказывает первое произнесение фразы. В Tiny 2:251
выбрана поздняя опора с расхождением +5,932 с и confidence=0,944;
ранний кандидат не расширялся из-за слабого ASR.
Источник: `_select_monotonic_anchor_skeleton`, `align_fast.py:1222`,
Tarteel chain и диагностика Tiny. Причина поздней речи — повтор в записи
или ошибка ASR — без прослушивания не установлена.
Исправление: последовательное разрешение текущей границы, поиск первой
поддержанной реализации, предыдущий хвост и проверка альтернатив внутри блока.

### P14 Confidence пропускает ошибки и смешивает оценки

**Дефект диагностики качества.** CTC местами использует
`max(conf_thresh, pause_sim, refined_conf)`; оценки разных происхождений
становятся одной confidence. Сохранённые benchmarks имеют крупные ошибки
с ненулевой confidence у всех трёх моделей.
Источник: `align_fast.py:9687,9800,10195` и корпусные отчёты ниже.
Исправление: решение об установленном факте отдельно от числового качества;
никакого поднятия слабого результата до порога. Хранить полноту фразы,
различающее слово, альтернативы, временную привязку и противоречия.
Калибровку вероятности делать на проверенном корпусе, а не выводить из `max`.

### P15 Неоднородная финальная валидация

**Дефект ограничения времени и риск неполной валидации.** Writer проверяет
ключи и строгий порядок, но не акустическую
доказанность, время внутри аудио и полный pause-контракт.
`pause_contract_violations` находится в benchmark; финальный monotonic guard
может увеличить метки без ограничения концом записи. Он ставит confidence=0,
но сам не гарантирует допустимую геометрию или совпадение всех trace-полей.
В сохранённом сравнении моделей отмечены две метки Phonetics 82:18/19
вне длительности аудио с confidence=0; это реальный пример нарушения
временного диапазона, а не только возможность в helper.
Источник: `project_db.py:157,172`, `align_fast.py:676`, `tools/bench_fast.py:54`.
Исправление: общий валидатор итогового объекта перед writer, проверка длительности
и доказательства. Перемещённая оценка остаётся предварительной; подтверждённую
pause-метку нельзя молча сдвинуть ради порядка.

### P16 Неполный снимок настроек CTC FAST

**Риск воспроизводимости.** CTC читает множество `SC_FAST_*` из env при импорте;
trace содержит подробные наблюдения, но не единый полный снимок эффективной
конфигурации. Tarteel сохраняет `fast_settings`, что не устраняет различие.
Источник: начало `align_fast.py`, `write_fast_trace`, строка 12730,
`align_fast_whisper.py:189`.
Исправление: одна неизменяемая конфигурация запуска, отдельные версии
алгоритма/адаптера/модели, полный снимок эффективных значений.

### P17 Большой объём накопленных эвристик

**Риск сопровождения.** `align_fast.py` содержит около 13,4 тысячи строк;
основная функция занимает почти 8 тысяч. Остались repair-лимиты и логика
для широких промежутков, которые теперь может отклонить локальный guard.
Тест helper сам по себе не доказывает, что соответствующая ветка достижима
и полезна при нынешних лимитах.
Исправление: переносить только необходимые операции и явно описанные переходы;
каждую сохраняемую repair-ветку связать со сценарием и допустимым окном.
Удаление старого кода завершает перенос; общего попутного рефакторинга нет.

### P18 Тест зависит от импорта GUI и порядка запуска

**Воспроизведённый дефект изоляции.** Первоначальная выборка тестов дала
252 passed, 1 failed, 7 skipped. Импорт Web GUI загружает выбранную модель
в глобальный `ACTIVE_ID`; `test_explicit_modes_are_not_replaced_by_reciter_reference`
после этого падает на проверке модели. Отдельно файл дал 5 passed;
перестановка той же выборки дала 253 passed.
Источник: `webgui/server.py:239`, `tests/test_pipeline.py:9`.
Исправление: убрать изменение активной модели при импорте, передавать выбранный
адаптер/снимок в запуск и явно задавать модель в тестах. Проверять порядок
исполнения с fake-адаптером без пользовательских настроек.

### P19 Исключения из центра паузы и защиты ручных меток

**Развилки контракта.** Обычный CTC возвращает метки в центры конечных пауз,
но opt-in fingerprint затем может уточнить время по началу клипа.
Benchmark освобождает `exact_fingerprint` и `ctc_pre_owner` от части проверок.
Источник: `align_fast.py:12677,13328`, `tools/bench_fast.py:54`.
Кроме того, writer поддерживает явный `overwrite_manual`, описанный в
`docs/project.md`, тогда как базовое правило AGENTS.md запрещает перезапись
edited/verified. По умолчанию ручные метки действительно защищены.
Это не обнаруженная самовольная перезапись при обычном FAST.
Решение для нового пути: соблюдать центр и защиту; fingerprint может быть
дополнительным свидетельством, но не сдвигать подтверждённую pause-метку.
Существующий отдельный fingerprint-режим не меняется. Политика сохранения
и явный выбор перезаписи принадлежат вызывающему коду, не адаптеру/executor.
Текущий запрос не разрешает перезаписать пользовательские данные; проверки
проводятся на временных БД. Расхождение AGENTS и описанного UI-исключения
не следует исправлять попутной сменой правил проекта.

## Проверки нового исполнителя

Нужны общие сценарные тесты для каждого адаптера и для fake-адаптера с заранее
заданными ответами. Проверяется последовательность событий и доказательства,
а не совпадение теста с внутренними строками реализации.

| Сценарий | Обязательный результат |
|---|---|
| Обычные различимые начала | Аяты подтверждаются по порядку, pause-метки в центрах |
| Первый аят с басмалой и без неё | Начало подтверждено локально без фиксированного сдвига к 6000 мс |
| Суры 1 и 9 | Канонические исключения сохраняются |
| Внутренняя пауза предыдущего аята | Не становится границей только из-за DSP или темпа |
| Похожие начала и внутренний повтор | До различающего слова нет подтверждения |
| Целое двухбуквенное слово | Разрешено обоснованное расширение, само слово не является окончательным доказательством |
| Точные начала 2:11 и 2:13 | Нет отказа только из-за похожего неполного конкурента |
| Общие первые шесть слов 2:68–70 | Проверяется дальнейшее различие либо явный совместный блок/ревью |
| Слияние слов или неполный ASR | Не подменяет канонический текст; выполняется разрешённая проверка либо ревью |
| Услышан будущий аят | Текущий номер не пропускается, правая гипотеза остаётся provisional |
| Повторное произнесение | Сильная поздняя фраза не отменяет раннюю без проверки контекста |
| Короткий и слишком широкий wasl | Первый проверяется локально; второй не вызывает FULL и остаётся для ревью |
| Длинная пауза плюс необходимая речь | План не обещает допустимое окно, которое затем отклонит guard |
| Нехватка бюджета, no pauses, слабый первый anchor | Причина ревью и confidence=0, нет скрытого прохода |
| Cache и повторные чтения | Sum/union учитывают реальные вызовы; cache hit не добавляет inference |
| Ошибка адаптера и отмена | Нет записи частичного результата и дальнейших вызовов |
| Нарушенный порядок или метка после конца | Общая валидация отклоняет недопустимый результат |
| Защищённые метки и конфликт | Writer сохраняет edited/verified, конфликт отклоняет транзакцию целиком |
| Новый адаптер и маршруты GUI/CLI | Та же точка входа и те же разрешённые переходы |
| Один и тот же неоднозначный ответ/cache hit | Конечное завершение recovery без расхода бюджета в бесконечном цикле |
| Ошибка/отмена внутри модели и повтор | Начатый вход учтён; неуспех не кешируется; повтор расходует бюджет |
| Отмена до cache hit или после commit | Первый не возвращает доказательство; второй не объявляет сохранённую суру несохранённой |
| Новый FAST при уже полном старом FAST | Auto пересчитывается по несовпадению run-key; edited/verified сохранены |
| Ручная правка во время расчёта | Merge проверен под транзакцией по актуальным данным, исходная модельная версия отдельно |
| Ошибка публикации JSON после commit | Явный исход сохранённой БД с ошибкой диагностики, без автоматического повторного inference |
| Удаление cache и повторная загрузка окна | Суммарный бюджет не сбрасывается; union остаётся корректным |
| Два подтверждения после округления совпали | Нет тихого сдвига; ревью/ошибка по общему контракту |
| Смена выбранной модели во время запуска | Bundle и provenance запуска остаются прежними |

Дополнительно нужны проверки зависимостей: адаптеры не вызывают executor,
writer, FULL/tiled или собственный обход всех пауз. На worker/RPC остаётся
проверка локального размера входа. Реальные аудиотесты проверяют счётчики
и отсутствие запрещённых вызовов независимо от trace самого адаптера.

Метрики качества сравниваются на одних записях и одинаковых DSP-паузах.
Сначала оценивают крупные ошибки среди подтверждённых границ, затем покрытие
подтверждениями, ошибки предварительных оценок и время. Алгоритм с ревью
всех аятов не считается улучшением только из-за отсутствия ложных подтверждений.
Снижение числа ревью ценой роста уверенных ошибок также не считается улучшением.
Порог крупного расхождения для сопоставимости со старыми отчётами — 500 мс;
это индикатор для слуховой проверки, не доказательство ошибки эталона.
До M3 фиксируются baseline, состав корпуса и следующие ворота по каждой
модели отдельно: ноль нарушений обязательных контрактов; ноль новых крупных
ошибок без ревью на слухово проверенных случаях; число таких ошибок не растёт;
доля подтверждений не падает относительно baseline. Метрики также разбиваются
на короткие/длинные суры, wasl, похожие начала и первый аят. Падение покрытия
в отдельной группе требует разбирательства, а не скрывается средним.
Если строгая политика остановки не проходит эти ворота, путь остаётся
экспериментальным; ослаблять правила после просмотра результатов нельзя.
Изменение заранее принятого порога — отдельная версия плана с обоснованием.

К корпусу 78–114 добавляются длинная сура, запись без вступительной басмалы,
длинная тишина, повтор чтения, недостаточное/обрезанное аудио, очень короткая
запись и данные другого чтеца при наличии. Отсутствующий материал отмечается
как непроверенный и ограничивает область вывода. Не скачивать данные и не
запускать дорогое полное выравнивание под видом проверки FAST.
Помимо качества измеряются load/decode/DSP/inference/matcher отдельно,
sum/union входа, peak RSS/cache и число обращений/отказов. Рефакторинг сам
по себе не обещает ускорения или повышения точности.

## Порядок внедрения

| Этап | Работа и условие перехода |
|---|---|
| M0: контракт и baseline | Зафиксировать рабочую копию (HEAD плюс diff/хэши новых файлов), параметры, конкретные конечные лимиты recovery/cache, доступные записи и старые результаты. Воспроизвести изоляцию тестов без пользовательских настроек. Старый и новый путь никогда не исполняются последовательно как fallback одного FAST-запуска |
| M1: шлюз и доказательства | Начатые попытки учтены независимо от исхода, отмена и cache согласованы; минимальные типы результата и общий валидатор протестированы без моделей. M1a — отдельная безопасная правка текущего guard, которую можно выполнить до дорогого corpus-baseline |
| M2: акустические адаптеры | Извлечь CTC и Tarteel операции, проверить карту канонических слов, независимый decode и реальные timing-capabilities. Каждый адаптер получает только разрешённый отрезок и не управляет порядком аятов |
| M3: один экспериментальный цикл | Сначала пройти fake-сценарии, затем подключить оба адаптера. Сразу выполнить P02–P06 и необходимые части P07–P15: отсутствие пропуска/предчтения, различающая фраза, допустимое окно, onset без фиктивного сдвига, честный estimate и итоговая валидация. Неподдерживаемый wasl остаётся review; качество модели не имитируется |
| M4: интеграция | Web/CLI/Qt/benchmark вызывают одну точку; run-key предотвращает пропуск старых auto-меток; bundle/config фиксированы. Сохранение учитывает manual overlay, отмену до/после commit и ошибку JSON. Проверки на временных БД, со сбоями и конкурентной ручной правкой |
| M5: ворота включения | Парное сравнение всех трёх моделей на зафиксированном корпусе, слуховая проверка новых крупных расхождений, контрактные тесты и проверки качества/покрытия выше. Пока ворота не пройдены, новый путь доступен только явно в экспериментальном harness и не становится штатным |
| M6: завершение | После прохождения ворот включить новый путь во всех точках и удалить самостоятельные старые циклы/ненужные repairs. Проверить оставшиеся ссылки, обновить project.md и STATUS; перечислить открытые P-ID и непроверенные записи |

Временный экспериментальный маршрут нужен только для сравнения и удаляется
в M6; он не является третьим постоянным алгоритмом FAST. Этапы дают отдельные
проверяемые изменения без автоматических коммитов. GPT-6.1 Sol / high выполнила
M1a; основной агент просмотрел результат. Ни M1a, ни один общий
`Protocol` не объявляются завершением архитектурной миграции.

Перенос не требует замены моделей, изменения выходной SQLite-схемы, нового
GUI или переписывания FULL. Он не должен затереть ручную разметку.

## Критерии завершения и оставшиеся решения

Архитектурная задача завершена, когда у FAST один исполнитель; обе модели
проходят его состояния; адаптеры не принимают бизнес-решения о границах;
guard и валидация общие; версия/настройки/причины сохраняются; все точки входа
используют новый маршрут; прежние самостоятельные циклы удалены; пройдены
ворота M5, не потеряны manual overlay, отмена, возобновление и честный исход
сохранения. Всё это проверяется на реализации, не наличием раздела в документе.
Остаточные проблемы качества перечисляются по P-ID, а не объявляются
автоматически исправленными из-за объединения кода.

Для M1a нерешённых вопросов нет. Для M0 нужны реальные значения ограничений
recovery/cache и зафиксированный корпус. Для M5 нужны доказательства качества
и достаточного покрытия. Будущее ослабление остановки хвоста, обрезание длинной
паузы или иной результат fingerprint — отдельные изменения контракта после
замеров. Изменять правила пользовательской перезаписи в рамках миграции не нужно.

Ревью документа выполнено; учтены R01–R09. Реализация общего исполнителя,
полное повторное измерение корпуса и слуховая проверка нового алгоритма
остаются впереди. Фактически выполненные правки и свежие тесты фиксируются
в [задаче исполнения](../2026-10-14-fast-contract-review/task.md).
