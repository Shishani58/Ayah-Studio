# Shatri fast-only all suras

## Цель

Расширить проверку fast-only Шатри с 78-114 на все 114 сур. Критерий:
сравнение с `abu_bakr_ash_shatri` reference, без запуска full-режима; найти и
исправить суры, где есть ошибки больше 500мс, особенно при повторяющихся началах
аятов.

## Решения

- Предыдущий `tools.bench_fast fast-only all` покрывал только 78-114; это
  недостаточно для цели пользователя.
- Нужно отдельное all-suras fast-only сравнение 1-114 и targeted trace для
  failures.
- Baseline 1-16 остановлен после подтверждения системной проблемы: длинные суры
  2-12 имеют очень мало pause anchors и большой wasl drift. Для дальнейшей
  итерации взяты меньшие воспроизводимые failures: 13, 55, 67, 78.
- Исправлены несколько классов ошибок:
  - timing для длинных/компактных пауз;
  - chain recovery перед future-gap;
  - сохранение far observed-current anchors после drift;
  - micro-pause steal с backtrack только на свободную предыдущую DSP-паузу;
  - ранний pending-current перед поздним confirmed на повторяющемся opening;
  - weak micro recovery между соседними anchors.
- Сура 67 доведена до max 484мс, 13 остаётся max 500мс, 78 max 497мс.
- Сура 55 улучшена с max 11909мс / <=500 74-76% до max 1660мс / <=500 97%;
  остатки: 2, 4, 26 по timing/refine, не по порядку повторов.

## Update 2026-06-30: средние суры и повторяющиеся openings

Проверка по средним сурам вместо слишком больших/малых:
`tools.bench_fast fast-only 036 037 056 075 076 080 083 089 098`.
Baseline: 37 имеет системный каскад (max 164620мс, <=500 62%); 36/56/80/83
имеют локальные ошибки; 75/76/89/98 зелёные.

Разобран основной повтор 37:66-70. Greedy выбирал позднее повторное
`fa-innahum...` на 514.73s вместо первого pause-backed старта 480.15s, затем
сдвигал `thumma inna...` и последующие аяты. Добавлен изолированный
pause-order/opening-run repair слой и unit-тест на слабую раннюю паузу перед
поздним confirmed repeat. Лучший промежуточный результат 37 был:
max 55508мс, p90 5834мс, <=500 75%, но попытки расширить greedy repair дальше
создавали регрессии или не закрывали блок полностью.

Контроль регрессий:
- `uv run pytest tests/test_align_fast.py -q` — 55 passed.
- `tools.bench_fast fast-only 023 037`: guard вернул 23 к max 463мс, но 37
  снова показывает исходный каскад, если repair слишком узкий.
- `tools.bench_fast fast-only 036 056 080 083 089 023 067 078`: 23 green,
  78/89 green, но 67 остаётся max 2700мс, 80/83 локально >500мс.

Вывод: дальше не расширять набор эвристик. Нужен настоящий локальный DP по
блоку повторяющихся openings: вход — несколько соседних аятов и свободные
pause-backed кандидаты; стоимость должна одновременно учитывать порядок,
prefix-сигнал для shared openings, fuzzy score только как вторичный сигнал,
и штраф за использование внутренних повторов. Непаузы по-прежнему допустимы
только для подтверждённого wasl.
