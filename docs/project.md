# project.md — архитектура и инварианты

Точка входа в документацию. Читать перед изменением архитектуры, пайплайна или
формата БД.

## Цель

Из папки аудио (один файл = одна сура, имена `001…114`) построить SQLite с
тайм-кодом **начала** каждого аята и дать **визуально-слуховую** проверку и
правку результата. Приоритеты: скорость, точность, лёгкость.

## Ключевая идея

Текст Корана статичен и известен. Поэтому это **forced alignment** (раскладка
известного текста по времени), а не распознавание речи. Конец аята = начало
следующего; конец последнего = конец файла → ищем только **старт каждого аята**.

## Пайплайн (гибрид, на суру)

1. Декод → PCM 16 kHz mono (bundled ffmpeg).
2. Известный чтец? → если есть готовые тайминги — берём напрямую.
3. Кандидаты: Silero VAD (паузы) + структурный приор (ожидаемые позиции по
   длинам аятов из `qpc_hafs`).
4. ONNX-модель один раз строит emissions для всей PCM-суры. Все последующие
   чтения пауз, расширение текстового контекста и локальные forced alignment
   используют только срезы сохранённых frames; trace фиксирует
   `emission_passes=1` и реальное покрытие аудио.
5. FAST сначала строит разреженный монотонный каркас высокоуверенных
   pause-owner. Для коротких и повторяющихся начал читается не первое уникальное
   слово, а минимум нормализованных букв с расширением до различающего слова
   текущего/следующего аята. Независимый последовательный проход подтверждает
   опоры; если соседние pause-кандидаты независимо указывают на одну пропущенную
   границу, весь спорный промежуток повторно сопоставляется по порядку между
   ближайшими подтверждёнными опорами. Для коротких начал этот локальный проход
   использует уже сохранённое широкое чтение паузы. Выбранная совместно
   последовательность защищена от последующих одноточечных repair-эвристик.
   Будущая опора ограничивает диапазон пауз, но не меняет временной prior внутри gap.
   Pause-backed метка остаётся строго в центре подтверждённой паузы.
6. Если между аятами нет подтверждённой паузы, FAST атомарно выравнивает весь
   wasl-участок между внешними pause-owner. Pause-backed границы получают центр
   своей паузы, а внутренние wasl-границы — CTC-start первого слова.
   Для оставшихся неуверенных границ проверяются возрастающие локальные
   окна: весь предыдущий аят и различающая начальная фраза текущего. Найденная
   сильная пауза может разделить эти два текста, чтобы первый распев или повтор
   не поглощался хвостом предыдущего аята. Принимается первое полное доказанное
   начало, а не наиболее уверенное позднее повторение. Слабое первое слово
   допустимо только у сильной паузы, если последующая фраза сама различает аят.
   Неполные CTC-пути и недочитанные окончания не подтверждают гипотезу.
   При доказанном предыдущем хвосте короткая слабая фраза проверяется ещё с
   одним целым словом, без снижения порога уверенности.
   Независимый greedy-декод отклоняет начало, если после него лучше слышен
   ещё не законченный хвост предыдущего аята. Перенос вперёд разрешён только
   когда старая метка попала внутрь доказанного предыдущего хвоста и это
   подтверждается тем же независимым сравнением, включая остаток слова.
   Проверка использует те же emissions; подробности — `joint_boundary_reads`
   в trace. Подтверждённые опоры и совместно решённые gaps не пересматриваются.
7. Опциональная fingerprint-проверка: если пользователь передал аятные клипы
   **той же записи**, FAST локально сверяет только доступные клипы по
   нормированной envelope-корреляции >=0.80 либо при согласии amplitude,
   log-energy и energy-delta. Совпадение принимается лишь при ограниченном
   локальном сдвиге и между соседними границами; сильный match может сделать
   только source-consensus-gated rollback назад (до 15 с), но не дальний шаг
   вперёд; исключительно сильный match допускает до 2.4 с вперёд. Дальний
   forward возможен только как согласованный блок двух подряд клипов, строго
   зажатый между неизменными соседями. Оно является независимым доказательством
   и может начаться сразу после pause-области.
   Сеть автоматически не используется.
8. Финальная структурная проверка ищет `insufficient_audio` и обратный порядок
   pause-owner. Только явно недочитанный участок выравнивается атомарно между ближайшими
   устойчивыми опорами; при инверсии отдельно перечитывается следующий
   опорный интервал, чтобы не оставить сдвинутый wasl-хвост. Один слабый аят не
   заменяет уже доказанные границы всей суры. Exact fallback остаётся для
   независимого глобального drift-сигнала или неустранимого нарушения порядка;
   на длинных сурах он выполняется bounded-тайлами, чтобы whole-sura CTC не
   создавал матрицу в сотни гигабайт.
9. Уверенность → флаги на ревью. Запись в рабочую БД.

Для воспроизводимого аудита `tools/bench_fast.py` принимает
`--ayah-audio-dir PATH`: он прогоняет тот же opt-in refine вместе с pause и
sequence контрактами.

## Модули

- `core/` — `decode`, `candidates`, `emissions`, `align`, `pipeline`.
- `data/` — `quran_text` (чтение `quran_mushaf.db`), `references` (эталоны/QUA),
  `project_db` (рабочая БД + merge), `export_db` (чистый экспорт).
- `gui/` — `app`, `dashboard_view`, `review_view`.
- `webgui/` — основной интерфейс: локальный FastAPI-сервер, webview, HTML/JS;
  `gui/` сохранён как прежний Qt-интерфейс.
- `cli.py` — батч.

## Данные

- `data/quran_mushaf.db` — таблица `words` (`qpc_hafs`): текст слов, карта
  слово→аят, число аятов на суру.
- `data/references/*.db` — ~45 размеченных чтецов (схема `timings`).
- `assets/fonts/qpc_hafs.ttf` — KFGQPC HAFS Uthmanic Script.

## Инварианты (не нарушать)

- Выход: схема `timings(sura, ayah, time)` (мс, старт аята) + `db_version`.
- Ровно 6236 аятов, 114 сур; `time` монотонно растёт внутри суры; число аятов
  на суру = из `quran_mushaf.db`.
- Соглашение про басмалу: для суры 1 аят 1 — басмала; для сур ≠1 вступительная
  басмала — интро, не приписывается аяту 1 (сверить с эталоном).
- Рабочая БД = валидная выходная БД + служебные таблицы (`review_meta`,
  `edit_history`); экспорт вырезает служебные таблицы.
- Перегенерация не затирает `edited`/`verified`.
- Strict-экспорт сверяет точный набор аятов с `quran_mushaf.db`, принимает
  только целочисленные неотрицательные старты со строгим порядком внутри суры.
  Экспорт поверх исходного проекта запрещён, включая ссылки на тот же файл;
  готовый экспорт заменяет назначение атомарно после успешной записи.
- Фоновая генерация использует снимок путей БД и аудио; её логи относятся
  к тому же проекту. Смена проекта во время фоновой генерации отклоняется.
- Возобновление пропускает только суры с полным каноническим набором аятов.
  Частичная ручная разметка сохраняется и не мешает досчитать остальные аяты.

## Метрики точности

Сверка с эталонным чтецом: median абс. ошибки старта < ~150 мс, 95p < ~500 мс.
